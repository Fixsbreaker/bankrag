# CLAUDE.md — правила проекта BankRAG

Этот файл лежит в корне репозитория. Правила действуют в каждой сессии и важнее любых других указаний.

## О проекте

BankRAG — помощник аналитика антифрода, который находит сети дропов (money mules).
- По графу переводов оценивает риск каждого счёта.
- По одному подтверждённому дропу находит похожие счета через векторный поиск (FAISS, HNSW).
- По каждому счёту готовит справку: сработавшие признаки, похожая типология схемы и нормы, с дословными цитатами из базы знаний (RAG без генеративной модели).

Система ничего не блокирует сама и не общается с клиентами. Решение всегда принимает аналитик.

Это студенческий проект для конкурса Ассоциации банков РК. Защита 10 ноября 2026, демо должно работать на ноутбуке.

## Жёсткие правила

### 1. Всё бесплатно
- Никаких платных API, облачных сервисов, подписок и пробных периодов, требующих карту.
- Никаких внешних LLM API (OpenAI, Anthropic, Google и т. п.).
- Только open-source библиотеки, которые ставятся через pip или brew.
- Данные — только открытые: набор IBM AML с Kaggle (бесплатный аккаунт), публичные тексты законов.

### 2. Всё локально
- Модели работают на машине пользователя, без интернета после первой загрузки.
- Модель эмбеддингов для текстов: `intfloat/multilingual-e5-small` через `sentence-transformers` на CPU. Она понимает русский и казахский и бесплатна. Модель скачивается один раз и кешируется.
- Генеративная LLM в ядре не используется — это архитектурное решение проекта. Справка собирается из найденных фрагментов по шаблону.
- Если понадобится перефразирование, только локально через Ollama и только с моего явного согласия. По умолчанию выключено.
- Всё должно работать на CPU, GPU не нужен.

### 3. Git
- Используй мой уже настроенный SSH-доступ к GitHub и существующий remote `origin` (вида `git@github.com:...`).
- Не меняй `git config` (user.name, user.email, remote URL) и не настраивай HTTPS или токены.
- Не добавляй в коммиты и PR строки `Co-Authored-By: Claude`, `Generated with Claude Code` и любые другие упоминания ИИ. Автор коммитов — я.
- Коммить небольшими логичными шагами, сообщения на английском в стиле `feat: ...`, `fix: ...`, `data: ...`.
- Перед `git push` спроси меня. Никогда не делай `push --force`, `reset --hard` по удалённой ветке и не переписывай историю.
- Не создавай репозитории, PR и issues через API или `gh`, если я не попросил.
- Не коммить данные, модели и секреты. В `.gitignore`: `data/raw/`, `data/processed/`, `models/`, `*.parquet`, `*.csv` крупнее 5 МБ, `.env`, `kaggle.json`.

### 4. Честность результатов
- Никогда не выдумывай метрики. Каждая цифра в README, отчётах и интерфейсе получается запуском скрипта и сохраняется в `reports/`.
- Никогда не выдумывай тексты законов и цитаты. В базе знаний только тексты, которые положил я. Где текста нет — ставь заглушку `TODO: вставить дословный текст из <URL>`, а не придумывай.
- Если результат плохой, так и пиши. Плохая честная цифра лучше красивой выдуманной.
- В интерфейсе и README указывай, что данные синтетические (IBM) и что казахстанские сценарии сгенерированы командой.

### 5. Как работать
- Сначала план, потом код. На крупные шаги показывай план и жди моего «ок».
- После каждого этапа: что сделано, как запустить, какие получились цифры, что дальше.
- Если что-то неясно или есть развилка (например, как определить метку «дроп»), спроси, а не решай молча.
- Не ставь пакеты глобально. Используй виртуальное окружение (`python -m venv .venv`) и `requirements.txt` с закреплёнными версиями.
- Если библиотеке нужен системный пакет (например, `brew install libomp` для LightGBM на macOS), скажи мне, а не ставь сам.
- Код на Python 3.11, с type hints, понятными именами и docstring у публичных функций. Комментарии и README на русском, идентификаторы на английском.
- Любой шаг, который долго считает (больше ~2 минут), должен иметь флаг для работы на выборке (`--sample`).
