# BankRAG

Помощник аналитика антифрода для выявления сетей дропов. Прототип.
Данные синтетические (IBM AML, NeurIPS 2023). Казахстанские сценарии сгенерированы командой. Решение принимает аналитик.

Система оценивает счета, находит счета с похожим поведением и готовит справку. Она ничего не блокирует и не общается с клиентами.

Путь аналитика: очередь счетов → карточка с причинами → «Найти похожие» с графом переводов → справка с дословными фрагментами базы знаний → решение «подтвердил» или «отклонил».

## Как запустить

Нужны macOS или Linux, Python 3.11 (или `uv`) и бесплатный токен Kaggle в `~/.kaggle/access_token`. На macOS для LightGBM нужен `brew install libomp`.

```bash
make setup    # окружение и зависимости
make data     # набор HI-Small с Kaggle, около 510 МБ
make build    # признаки, модели, индексы
make eval     # метрики в reports/
make app      # интерфейс на http://localhost:8501
```

`make test` запускает тесты. Без интернета интерфейс работает после первой загрузки модели эмбеддингов.

Интерфейс в Docker, на артефактах, уже подготовленных шагами `make build` и `make eval`:

```bash
docker compose up
```

## Результаты

Все числа получены запуском и записаны в [reports/metrics.md](reports/metrics.md). Настройки и пороги выбраны на валидации.

### Тест IBM без хвоста

354 447 счетов, 97 дропов, доля дропов 0,027%.

| Метод | Тревог | Найдено дропов | Precision | Recall | F1 | PR-AUC (95% интервал) |
| --- | --- | --- | --- | --- | --- | --- |
| Правило, подобранное на валидации | 909 | 11 из 97 | 1,2% | 11,3% | 2,2% | — |
| LightGBM | 204 | 58 из 97 | 28,4% | 59,8% | 38,5% | 0,459 (0,374–0,556) |
| Быстрый транзит | 17 | 0 из 97 | 0,0% | 0,0% | 0,0% | — |

- При 909 тревогах модель находит 73 дропа, правило 11, то есть на 62 больше.
- Первые 100 подсказок модели: 41 дроп, 22 прочих помеченных, 37 ложных тревог.
- «Найти похожие»: Precision@10 10,7%, запрос 0,10 мс в среднем и 0,13 мс p95, индекс на 354 тыс. счетов строится около 30–40 с.

Тест с хвостом выглядит лучше (F1 65,2%), но там задача заметно легче, поэтому он показан только в отчёте для сравнения.

## Ограничения

- **Данные синтетические.** На реальных данных банка система не проверялась.
- **Модель не переносится на другую схему.** LightGBM обучена на дропах IBM и не находит дропов казахстанских сценариев: там быстрый транзит в одной валюте, в IBM дропы медленнее и используют несколько валют. Вероятно, модель учит и особенности генератора IBM.
- **Сценарии сгенерированы командой.** Параметры не откалиброваны на реальных данных. Правило быстрого транзита ищет именно то, что заложено в генератор, поэтому его цифры показывают, что система умеет ловить такую схему, а не то, что она сработает в реальном банке. Сети одного генератора похожи друг на друга сильнее настоящих, это завышает и Precision@10.
- **Мало дропов.** В тесте их 97, поэтому интервалы широкие.
- **Справка не определяет тип схемы.** Подбор типологии по тексту не лучше случайного: первый фрагмент совпадает со схемой примерно в 26% случаев, как и случайный выбор. Порог близости выбран по нескольким проверочным запросам.
- **Норм в базе знаний пока нет.** Текст ст. 232-1 УК РК нужно вставить в `kb/law_232_1.md`, затем пересобрать индекс базы знаний. До этого справка пишет, что нормы не найдены.
- **Не замена антифрода.** Это подсказки аналитику, а не решения.
- **Несколько копий OpenMP на macOS.** LightGBM работает отдельным процессом, а FAISS и torch в одном процессе работают в один поток с флагом `KMP_DUPLICATE_LIB_OK`. Подробности в `src/bankrag/faiss_safe.py`.

## Методика

### Метка «дроп»

В наборе IBM метки стоят на переводах, а система оценивает счета. Метка счёта считается так:

- **дроп** — счёт и получал, и отправлял помеченные переводы, то есть был посредником в цепочке;
- **прочие помеченные** — остальные счета с помеченными переводами, например начало и конец цепочки. В метриках они не считаются ни дропами, ни чистыми;
- **чистые** — все остальные счета.

Помеченный перевод самому себе не делает счёт посредником.

### Разбиение по времени

Разбиение 60/20/20 считается по числу транзакций, а не по календарю, порядок по времени сохраняется.
В конце периода IBM обычных переводов почти нет: после 10 сентября 2022 осталось 1 108 переводов, из них 59% помечены.
Календарные доли оставили бы в тесте 123 перевода, поэтому метрики считаются на тесте с этим хвостом и без него.

Метка считается отдельно по транзакциям каждого окна. Счёт, который получал помеченные переводы в одном окне, а отправлял в другом, в каждом из них попадает в «прочие помеченные». Цифры по периодам: `reports/labels_summary.json`.

### Признаки

Признаки считаются за окно 48 часов одной длины во всех периодах: счётчики за разное время несравнимы.
Окна обучения перекрываются с шагом 12 часов, поэтому один счёт встречается в них несколько раз; валидация и тест используют по одному окну.
Суммы приводятся к долларам по курсам, выведенным из переводов с конвертацией за период обучения: своих курсов в наборе нет. Для тенге курс задан в настройках как допущение.
Признак «связь с известными дропами» использует только дропы, известные до начала окна.

### Модель и правила

Правило-ориентир и настройки LightGBM подбирались только на валидации. Тест при выборе не использовался.
LightGBM работает отдельным процессом и сохраняет оценки и причины в файл, интерфейс читает готовый результат.

Правило быстрого транзита — второй сигнал очереди: отправителей не меньше 3, транзит 80–120%, пересылка не дольше 60 минут. Пороги заданы вручную и выбирались на сетях другого seed.

### Похожие счета

Вектор счёта — стандартизованные признаки с логарифмом счётчиков. Масштаб обучен на периоде обучения. Индекс FAISS HNSW, метрика косинус: она сравнивает профиль поведения, а не размер счёта, и на валидации немного лучше L2 (27,7% против 25,8%).

### Справка

Причины счёта превращаются в текстовый запрос, модель `intfloat/multilingual-e5-small` локально находит близкие фрагменты базы знаний, и они выводятся дословно с источником. Генеративной модели нет. Описания типологий — пересказ статьи IBM авторами проекта, а не цитата.
