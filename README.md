# BankRAG

Чат-помощник аналитика антифрода. Прототип.
Данные синтетические: IBM AML (NeurIPS 2023) и казахстанский сценарий, сгенерированный командой. Решение принимает аналитик.

Аналитик пишет вопрос обычными словами: «куда ушли деньги клиентки?», «кто ещё переводил на этот счёт?», «подготовь справку». Локальная модель Qwen3 через Ollama выбирает нужную функцию и коротко пересказывает её результат. Все числа считает код, а не модель. Помощник ничего не блокирует и не записывает решения: это делает человек кнопкой.

## Главный сценарий

Клиентке позвонили «из службы безопасности банка», и 3 ноября в 14:05 она перевела 500 000 ₸ на счёт `KZ-1654`. Вечером она пишет в банк. Аналитик задаёт вопросы:

1. «Куда ушли деньги?» — за 2 ч 41 мин деньги прошли 4 счёта: `KZ-1654` → `KZ-4753` → два счёта примерно поровну → снятие наличных. Снято 453 000 ₸, на счетах осталось 47 000 ₸.
2. «Покажи на графе» — граф, где счета окрашены по уровню подозрения.
3. «Кто ещё переводил на KZ-1654?» — 10 переводов от 10 отправителей на 4,2 млн ₸, жалобы ещё у двух человек.
4. «Какая статья к этому относится?» — дословный текст ст. 232-1 УК РК из базы знаний со ссылкой на adilet.zan.kz.
5. «Подготовь справку для полиции» — файл DOCX: таблица движения денег, граф, флажки счетов, текст статьи.
6. «Заблокируй KZ-1654» — отказ: приостановку делает аналитик в системах банка.
7. Аналитик нажимает «Подтвердить» у счетов, решение попадает в журнал.

Счета и суммы взяты из сгенерированного сценария (`reports/demo_case.json`, seed 2026). Порядок вопросов для показа: [scripts/demo_questions.md](scripts/demo_questions.md).

## Как запустить

Нужны macOS или Linux, Python 3.11 (или `uv`), бесплатный токен Kaggle в `~/.kaggle/access_token`, на macOS — `brew install libomp` для LightGBM.

Языковая модель ставится один раз (около 14 ГБ на обе модели):

```bash
brew install ollama
brew services start ollama
ollama pull qwen3:14b
ollama pull qwen3:8b
```

Запуск за 5 команд:

```bash
make setup    # окружение и зависимости
make data     # набор HI-Small с Kaggle (около 510 МБ) и перечни АФМ РК
make build    # признаки, модели, индексы, казахстанский сценарий
make eval     # метрики в reports/
make app      # проверяет Ollama и открывает чат на http://localhost:8501
```

`make test` запускает тесты, Ollama для них не нужна: модель подменяется заглушкой. `make check-llm` проверяет, что модель отвечает и вызывает функции. `make chat-eval` оценивает чат на 33 вопросах для обеих моделей.

Если Ollama не запущена, приложение работает в режиме кнопок: «Проследить деньги», «Откуда пришли деньги», «Показать сеть», «Справка» вызывают те же функции, ответ собирается по шаблону.

## Как устроено

```
вопрос → Qwen3 выбирает функцию → функция считает по данным → Qwen3 пишет короткий ответ → проверка чисел → ответ
                                                                                                         ↓
                                                                                                      журнал
```

Функции чата (`src/bankrag/tools/functions.py`):

| Функция | Что делает |
| --- | --- |
| `trace_money` | идёт по ходу денег от поступления: кому, сколько, через сколько, где сняли наличными |
| `trace_sources` | кто переводил на счёт, сколько и есть ли у отправителей жалобы |
| `account_profile` | флажки понятными фразами, оценка модели риска, основные числа |
| `find_network` | счета, реально связанные переводами, с цветом подозрения |
| `find_similar` | счета с похожим поведением через FAISS HNSW; они не обязательно связаны переводами |
| `list_suspicious` | самые подозрительные счета за день или период |
| `search_knowledge` | дословные фрагменты базы знаний и источник |
| `check_lists` | сверка владельца счёта и его контрагентов с перечнями АФМ РК |
| `make_report` | справка DOCX |
| `show_graph` | граф из последнего результата |

Функций блокировки и записи решений у модели нет.

### Флажки

Счёт получает флажок, когда срабатывает простое правило. Пороги в `configs/config.yaml`.

| Флажок | Правило |
| --- | --- |
| Транзит | за 72 ч после поступлений ушло дальше не меньше 80% полученного |
| Вывод наличными | снятие наличных в течение 72 ч после поступления, не меньше половины поступления |
| Быстрая пересылка | половина поступления ушла дальше быстрее чем за 60 минут, даже частями |
| Много отправителей | 5 и больше разных отправителей за сутки (кроме магазинов и работодателей) |
| Дробление | поступление разослано на 2 и больше счёта примерно равными частями |
| Связь с дропом | переводы со счётом, который аналитик подтвердил |

Покупки в магазинах пересылкой не считаются. Пороги стартовые, из обсуждения команды, на тестовом наборе не подбирались.

### Проверка по перечням АФМ

Банк обязан проверять клиентов и контрагентов по перечням Агентства по финансовому мониторингу. BankRAG делает это так:

1. `make lists` скачивает четыре перечня из открытого API АФМ `api.websfm.kz` (ключ не нужен) в `data/raw/lists/`: лица, связанные с финансированием терроризма и экстремизма; причастные к террористической деятельности; ФРОМУ; санкционный перечень СБ ООН. Дата загрузки сохраняется, перечни можно обновлять каждый день. После загрузки интернет не нужен.
2. У счетов казахстанского сценария есть вымышленные владельцы (`src/bankrag/owners.py`): ФИО, дата рождения и ИИН у клиентов, название ТОО и БИН у магазинов и работодателей. ИИН и БИН нарочно недействительны (неверная контрольная цифра). Сгенерированные ФИО, которые случайно совпали с записью настоящего перечня, пропускаются.
3. Совпадение считается по ИИН/БИН, по названию организации или по ФИО вместе с датой рождения. Однофамилец с другой датой рождения — не совпадение. Если в перечне даты нет, совпадение по ФИО помечается «проверить». Похожее написание не ищется.
4. Счёт лица из перечня всегда красный и стоит первым в очереди. У его контрагентов в профиле видно, что они переводили лицу из перечня. Раздел «Проверка по перечням АФМ» есть в справке.

Для демо в `configs/watchlist_demo.json` лежит одна вымышленная запись в формате API — «ТОО «Тестовая запись BankRAG»», её получил один магазин сценария. Реальным лицам из перечней синтетические переводы не приписываются. Итог сверки — `reports/watchlist.json`.

### Цвета на графе

- **Красный** — подозрительно: владелец в перечне АФМ, 2 и больше флажков или риск модели выше порога тревоги.
- **Оранжевый** — стоит проверить: 1 флажок или риск выше половины порога.
- **Серый** — нейтрально: флажков нет, истории мало.
- **Зелёный** — чисто: 5 и больше переводов, флажков нет, риск низкий.
- **Синий** — пострадавший: есть жалоба.
- Толстая рамка — счёт подтверждён аналитиком.
- Оттенки подобраны так, чтобы различаться и по светлоте: цвет никогда не единственный признак, рядом всегда идёт подпись и число флажков. Это важно при дальтонизме и в чёрно-белой распечатке справки.

### Защита от выдумок

- Модель получает от функции итоговые числа и готовые строки («480 000 ₸», «через 13 мин») и переписывает их.
- Перед показом код находит в ответе все числа, время и номера счетов (с пробелами в тысячах, запятыми, «млн», %) и сверяет их с результатами функций этого хода, вопросом и предыдущим результатом. Если не сходится — одна повторная попытка, потом ответ по шаблону из результата.
- На вопрос о счёте или законе модель обязана вызвать функцию: ответ без неё не показывается.
- Текст закона выводит код дословно под ответом, модель его не видит и не пересказывает.
- Под каждым ответом блок «Как получен ответ»: какие функции вызваны, с какими параметрами и что вернули.
- Каждый вопрос, вызовы функций, ответ и решения аналитика пишутся в локальный журнал (SQLite), вкладка «Журнал».

## Результаты

Все числа получены запуском и записаны в `reports/`.

### Чат: 33 вопроса

`reports/chat_metrics.md`, запуск `make chat-eval`. 28 вопросов с ожидаемой функцией (из них 3 о перечнях АФМ) и 5 на отказ («заблокируй», «где живёт владелец», несуществующий счёт, вопрос не по теме, «позвони клиенту»). MacBook Pro M1 Pro, 32 ГБ.

| Модель | Верная функция | Верные параметры | Первый ответ не прошёл проверку чисел | Верные отказы | Время, среднее / p95 |
| --- | --- | --- | --- | --- | --- |
| qwen3:14b | 28 из 28 | 28 из 28 | 0 из 33 | 5 из 5 | 14,2 / 24,9 с |
| qwen3:8b | 28 из 28 | 28 из 28 | 0 из 33 | 4 из 5 | 8,2 / 16,8 с |

Основная модель — `qwen3:14b`. `qwen3:8b` быстрее, но на просьбу «напиши стихотворение про осень» написала стихотворение вместо отказа. В прошлом прогоне на 30 вопросах она ошиблась в другом месте: выдумала, что «счетов в других банках нет». 33 вопроса — маленькая проверка, а не гарантия.

### Казахстанский сценарий

31 сеть (одна — демо-кейс), 171 дроп, 2 618 счетов фона, 86 жалоб, seed 2026. `reports/metrics.md`.

| Метод | Найдено дропов | Найдено сетей | Тревог на счетах фона |
| --- | --- | --- | --- |
| Флажки: 2 и больше (красный) | 147 из 171 | 31 из 31 | 12 |
| Флажки: хотя бы один | 171 из 171 | 31 из 31 | 34 |
| Быстрый транзит (прежнее правило) | 29 из 171 | 28 из 31 | 0 |
| LightGBM | 1 из 171 | 1 из 31 | 0 |

Флажки и сценарий придумала одна команда, поэтому высокие цифры ожидаемы и не переносятся на реальный банк. «Найти похожие» от дропов сценария даёт Precision@10 99,9% по той же причине: сети одного генератора очень похожи друг на друга.

### Модель риска на тесте IBM

354 447 счетов, 97 дропов. LightGBM: 204 тревоги, найдено 58 из 97, PR-AUC 0,459 (95% интервал 0,374–0,556). Правило-ориентир при 909 тревогах находит 11.

**Проверка модели** (`reports/model_audit.json`, `python -m bankrag.model_audit`). У 100 счетов с наибольшим риском заметную часть оценки дают признаки «разных валют», «переводов самому себе» и «форматов платежа». Это особенности генератора IBM, а не поведение дропа. Без них модель заметно хуже:

| Признаки | PR-AUC на валидации | PR-AUC на тесте | Найдено дропов на тесте | Дропов в первых 100 |
| --- | --- | --- | --- | --- |
| все 16 | 0,672 | 0,459 | 58 из 97 (204 тревоги) | 48 |
| без трёх подозрительных | 0,324 | 0,243 | 33 из 97 (170 тревог) | 30 |

Значит, примерно половина качества модели на IBM держится на особенностях синтетики. В объяснениях аналитику эти признаки не показываются.

## Ограничения

- **Данные синтетические.** На реальных данных банка система не проверялась. Казахстанский сценарий и его фон (зарплаты, покупки, переводы родственникам) сгенерированы командой, параметры не откалиброваны на реальных данных.
- **Флажки ищут то, что заложено в генератор.** На сценарии они хорошо отделяют дропов, но это показывает, что система умеет ловить такую схему, а не то, что она сработает в реальном банке.
- **Модель риска держится на особенностях синтетики IBM** (см. результаты) и не переносится на казахстанский сценарий. Поэтому цвет на графе определяют в основном флажки.
- **`Cash` в IBM — не снятие наличных.** Проверено на данных: в 97,7% таких платежей получатель в другом банке, 94% получателей сами потом переводят деньги дальше. Поэтому на IBM флажок «вывод наличными» не срабатывает. В казахстанском сценарии снятие задано явно: перевод на банкомат.
- **Сверка по перечням — точное совпадение.** Опечатки и разная транслитерация не учитываются, в записях API сейчас почти нет ИИН. В банке для этого есть отдельные системы проверки по спискам; BankRAG показывает их результат аналитику, а не заменяет их. Владельцы счетов в сценарии вымышлены.
- **Нормы показываются для сведения.** В базе знаний дословный текст ст. 232-1 УК РК с adilet.zan.kz на 1 ноября 2026 года. Правовую оценку даёт уполномоченный орган.
- **Время ответа** зависит от компьютера: замеры сделаны на MacBook Pro M1 Pro, 32 ГБ.
- **Несколько копий OpenMP на macOS.** LightGBM работает отдельным процессом, интерфейс читает готовые оценки. Подробности в `src/bankrag/faiss_safe.py`.

## Методика модели риска

### Метка «дроп»

В наборе IBM метки стоят на переводах, а система оценивает счета:

- **дроп** — счёт и получал, и отправлял помеченные переводы, то есть был посредником в цепочке;
- **прочие помеченные** — остальные счета с помеченными переводами, в метриках не считаются;
- **чистые** — все остальные.

### Разбиение и признаки

Разбиение 60/20/20 по числу транзакций, порядок по времени сохраняется. В конце периода IBM обычных переводов почти нет, поэтому тест считается с этим хвостом и без него. Признаки считаются за окно 48 часов, окна обучения перекрываются с шагом 12 часов. Суммы приводятся к долларам по курсам из переводов с конвертацией; для тенге курс 500 задан как допущение. Настройки LightGBM и порог тревоги подбирались только на валидации.

Аналитику показываются только понятные причины модели: число отправителей и получателей, доля транзита, скорость пересылки, ночные операции, связь с известными дропами.

### Похожие счета

Вектор счёта — стандартизованные признаки с логарифмом счётчиков, индекс FAISS HNSW с косинусной метрикой.
